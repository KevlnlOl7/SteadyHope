# 7/30 進度報告 demo 流程

## A. STM32現場demo（優先）

上台前先關閉馬達或禁止H-bridge輸出。本段只驗證gating判斷，不驗證人體抑震。

CubeIDE Watch建議顯示：

- `selectedGyroInputDps`
- `bandpass_tremor_envelope`
- `bandpass_voluntary_envelope`
- `bandpass_tremor_ratio`
- `bandpass_on_count`
- `bandpass_off_count`
- `bandpass_gate_enabled`

展示順序：

1. 選擇1 Hz、15 deg/s測試陣列，執行後指出`enabled`維持0。
2. 選擇5 Hz、15 deg/s測試陣列，指出訊號開始約520 ms後`enabled`變成1。
3. 選擇7 Hz、15 deg/s測試陣列，指出`enabled`維持0。
4. 說明板上輸入流程是「CSV轉C測試陣列 → STM32 gating → IDE輸出」，不是STM32直接讀CSV。
5. 主動補充：這只驗證人工Gyro資料下的開關判斷，不代表馬達力量或抑震率。

## B. 離線備援demo

若板子、CubeIDE或接線臨時失敗，在repo根目錄執行：

```powershell
python algorithms/validation/weekly_demo.py
```

程式會依序顯示：

1. 1～8 Hz在15 deg/s下的gating預期結果。
2. 7 Hz從15提高到20 deg/s時可能誤開。
3. 實際取樣率105 Hz時，4 Hz邊界可能漏判。
4. App 400筆BLE fixture的5 Hz與4～6 Hz RMS驗收答案。

若老師要求看自動測試，再執行：

```powershell
python -m unittest discover -s algorithms/validation -p "test_*.py"
```

## 不要現場做的事

- 不要臨時把未完成的腕部雛形通電套在人身上。
- 不要把`enabled=1`說成已經抑震。
- 不要使用eHWFLC-KF的`freqEstimate`作為App震顫頻率。
- 不要把合成訊號結果說成患者成效或真實抑震率。
